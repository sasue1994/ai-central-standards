## Multi-agent orchestration — เมื่อมี agent มากกว่าหนึ่งตัว

มาตรฐานนี้ใช้เมื่องานถูกแบ่งให้หลาย agent ทำ โดยมี **orchestrator agent** เป็นตัวกลาง
วิเคราะห์ความต้องการ แตกงาน มอบหมาย และรวมผล — ไม่ใช่ให้ทุก agent เดางานเอง
(ใช้คู่กับ `core/workflow.md` ที่เป็น loop การทำงานของ agent เดี่ยว)

### หลักการสูงสุด — ห้ามคิด/เดาเอง
- orchestrator และ sub-agent **ห้ามเดา requirement, ห้ามสมมติ scope, ห้ามเติมสิ่งที่ผู้ใช้ไม่ได้สั่ง**
- สงสัยเรื่อง **ความต้องการ/ขอบเขต/ลำดับความสำคัญ** → ถาม **ผู้ใช้**
- สงสัยเรื่อง **เทคนิค/สถานะงาน/ผลลัพธ์ของอีก agent** → ถาม **agent ที่เกี่ยวข้องโดยตรง**
- ถ้าไม่มีข้อมูลพอจะลงมือ → **หยุดแล้วถาม** ดีกว่าลงมือบนสมมติฐานที่ผิด

### Step 1 — Orchestrator วิเคราะห์ requirement ก่อนเสมอ
ก่อนแตกงานใด ๆ orchestrator ต้อง:
1. สรุป requirement ที่ได้รับกลับมาเป็นภาษาคน (สิ่งที่เข้าใจ) เพื่อยืนยันกับผู้ใช้
2. ระบุ **ความกำกวม** ที่ยังตอบไม่ได้จาก context — ถามผู้ใช้ทีละคำถามที่เป็น blocker จริง
   (ขอบเขต, ข้อจำกัด, environment, definition of done, ลำดับความสำคัญ)
3. อย่าเริ่ม Step 2 จนกว่าความกำกวมที่เป็น blocker จะถูกเคลียร์

ห้ามข้ามขั้นนี้เพื่อ "รีบทำ" — requirement ที่เข้าใจผิดทำให้ทุก sub-task ที่แตกออกไปเสียเปล่า

### Step 2 — แตกงานเป็น task ที่ชัดเจนต่อ agent
orchestrator แปลง requirement เป็นชุด task โดยแต่ละ task ต้องระบุครบ:
- **objective** — เป้าหมายของ task เป็นประโยคเดียว
- **owner** — agent/บทบาทที่รับผิดชอบ (หนึ่ง task มีเจ้าของชัดเจนหนึ่งราย)
- **scope / out-of-scope** — ทำอะไร และ **ไม่ต้องทำ** อะไร (กัน scope creep)
- **inputs** — ข้อมูล/ไฟล์/ผลจาก task ก่อนหน้าที่ต้องใช้
- **deliverable** — ผลลัพธ์ที่ต้องส่งกลับ และรูปแบบ
- **definition of done** — เงื่อนไขที่ถือว่าเสร็จ (ทดสอบผ่าน, ผ่าน review, ฯลฯ)
- **dependencies** — task นี้ต้องรอ task ไหนก่อน (ถ้ามี)

หลักการแตกงาน:
- แต่ละ task **แยกกันได้ (independent)** เท่าที่เป็นไปได้ เพื่อทำขนานกัน; ระบุ dependency เฉพาะที่จำเป็นจริง
- task ต้อง **เล็กพอจะตรวจได้** — ถ้าใหญ่เกินจะพิสูจน์ผลยาก ให้แตกย่อยอีก
- ไม่มอบสอง task ที่แก้ไฟล์/ทรัพยากรเดียวกันแบบชนกันให้รันขนาน — จัดลำดับหรือรวมเป็น task เดียว

### Step 3 — มอบหมายและติดตาม
- ส่ง task ให้ owner พร้อม context ครบตาม Step 2 — อย่าให้ sub-agent ต้องเดา input ที่หายไป
- ถ้า sub-agent ติดขัดหรือเจอความกำกวม ให้ **ยกกลับมาที่ orchestrator** ไม่ใช่ตัดสินใจเดาเอง
- orchestrator เป็นคนตัดสินว่า blocker นั้นต้องถาม **ผู้ใช้** (requirement) หรือถาม **agent อื่น** (เทคนิค/สถานะ)
- เปลี่ยน requirement กลางทาง → orchestrator ประเมินผลกระทบต่อ task ที่ค้าง แล้วแจ้ง/ปรับก่อนไปต่อ

### Step 4 — รวมผลและตรวจก่อนส่ง
- orchestrator รวม deliverable จากทุก task ตรวจว่า **ครบตาม requirement เดิม** และ task ต่อกันได้จริง (ไม่ขัดกันเอง)
- ถ้าผลจาก sub-agent ขัดแย้งกัน → **ไม่เลือกเดา** ให้สอบถาม agent ที่เกี่ยวข้องหรือผู้ใช้เพื่อชี้ขาด
- รายงานกลับผู้ใช้ด้วย **หลักฐาน** (ไฟล์ที่เปลี่ยน, ผล test/lint จริง) ไม่ใช่คำยืนยันลอย ๆ — ตาม Definition of done ใน `core/conventions.md`

### What NOT to do
- ห้าม orchestrator ลงมือแตกงานทั้งที่ requirement ยังกำกวม — ต้องเคลียร์กับผู้ใช้ก่อน
- ห้าม sub-agent เติม scope หรือเดา input ที่หายไป — ยกกลับมาถาม
- ห้ามมอบ task ที่ไม่มี definition of done ชัดเจน
- ห้ามรวมผลแล้วรายงานว่า "เสร็จ" โดยไม่มีหลักฐานว่าแต่ละ task ผ่าน definition of done
- ห้ามให้สอง agent ตัดสินใจทับกันบนไฟล์/ทรัพยากรเดียวกันโดยไม่มี orchestrator ชี้ขาด
